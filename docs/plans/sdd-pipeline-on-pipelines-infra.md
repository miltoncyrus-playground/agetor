## 1. Objective & success criteria

Today's SDD flow is bespoke orchestrator code keyed off `task.pipelineStage` (specify → clarify → planning → plan-review → decompose → building → code-review → testing → done), with a dense layer of deterministic token-efficiency work on top of it (O-1…O-15 in `pipeline-token-efficiency.md`). PR #244 ships a generic, visually-authored step-graph runner with its own execution model (parent task + hidden step tasks, agent-authored `<handoff>` blocks, fan-out/join, freeze-at-run-start). The two systems are structurally incompatible today — different Task fields, different handoff mechanisms, no shared discriminator.

Done means:

1. A committed, importable pipeline definition (`agetor pipeline import`) that expresses the SDD flow as steps + edges on #244's `PipelineGraph` shape — authored once, not hand-clicked per run.
2. Every token-efficiency mechanism from O-1…O-15 ported and re-keyed off `isPipelineStepTask(task)` (PR #244's own discriminator, `pipeline-runner.ts:98`) instead of `task.pipelineStage`, with **zero new migrations** — the integration reuses #244's `pipelines`/`tasks.pipeline_*` columns wholesale.
3. Decompose → Build uses #244's native `transition:"all"` / `join:"all"` (fan-out/join), not `build-scheduler.ts`'s separate-worktree-plus-merge machinery — per the user's explicit decision in the PR #244 comment already posted.
4. The Plan-Review human gate is preserved functionally (not structurally — see §3 D5).
5. A same-ticket parity run (legacy `pipelineStage` flow vs. the new graph) shows no token-cost regression beyond the one bounded, unavoidable gap identified in §3 D6, and no correctness/outcome regression.
6. Retiring the legacy `pipelineStage` orchestrator path is explicitly **not** part of this plan's done-criteria — it's a follow-up once parity is proven on real tickets.

## 2. Context & constraints (Phase 1 findings)

- **Lean context** — `pipelineLeanContext` (`src/bun/orchestrator.ts:1194`), applied at `:1864`. Strips tool set to `Read,Edit,Write,Bash,Grep,Glob` (+`AskUserQuestion` for clarify), sets `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1` + `--append-system-prompt-file`, `CLAUDE_CODE_DISABLE_BUNDLED_SKILLS=1`. Keyed today on "is a pipeline task" via `task.pipelineStage != null`.
- **CLAUDE.md filtering** — `resolvePipelineSystemPromptFile` (`orchestrator.ts:1229`) → `filterClaudeMdForPipeline` (`claude-md-filter.ts:208`), with `cutOrchestrationFlowStageGate` (`:116`, drops the Orchestration-flow tail wholesale for non-coding stages) and `cutOrchestrationFlowOverlap` (`:158`, files-overlap trim for coding stages, using `inLane` from `stage-handoff.ts:286`). **This is stage-aware** — it needs to know "is this stage coding or non-coding," which is the crux of §3 D3 below.
- **Effort/model tiering** — `resolveRunModel` (`orchestrator.ts:1168`), `resolveRunEffort` (`:1324`). Verdict stages get `low`, build children get `medium`.
- **Deterministic stage-handoff** — `extractHandoff` (`stage-handoff.ts:222`), `renderHandoff` (`:320`). Harvests each settled stage's Read paths + succeeded commands from `run_events`/JSONL — never trusts the agent to self-report it.
- **Precheck + Tester-skip** — `pipeline-precheck.ts`: `precheckPasses` (`:75`), `precheckPassedChecks` (`:82`), `testerSkipEnabled` (`:89`). Invoked from `runTesterGate` (`orchestrator.ts:2906`, called at `:3750`) — **this is orchestrator-side deterministic code that runs BETWEEN Code-Review's settle and the Tester's launch, and can skip spawning the Tester agent turn entirely.** There has never been a separate "Precheck" agent stage — this matters for §3 D6.
- **Review-diff caching** — `review-diff.ts`: `reviewDiffPath` (`:50`), `capStat` (`:61`). Writes the Code Reviewer's diff once; a revision pass diffs since last-reviewed sha.
- **Repo-profile detect-once** — `repo-profile.ts`: `detectRepoProfileFromFiles` (`:116`), `renderProjectCommands` (`:207`). Purely cwd-scoped, never stage-aware — portable unchanged.
- **Decompose sizing** — prompt-text logic sizing subtask slices (soft cap ~8 files/slice). Pure prompt generation, portable as static instructions text on whichever step emits it.
- **Session-close-on-settle** — `dropSettledStageSession` (`orchestrator.ts:2879`). Likely redundant under #244 — each step is already its own `tasks` row with its own session lifecycle; verify during T3 (§4) rather than assume.
- **Parallel build (today)** — `build-scheduler.ts`: `subtaskFilesForChild` (`:24`), `buildBarrierState` (`:97`). Separate worktree per child + agent-assisted merge-back on conflict. **Explicitly not reused** by the new graph per the user's decision — stays in the codebase for now, unused by this pipeline definition.

### Pipelines side — `upstream/feature/agetor-pipelines` (PR #244), not yet in fork `main`

- **Discriminator** — `isPipelineStepTask(t: Task)` (`pipeline-runner.ts:98`) — the natural drop-in replacement for `task.pipelineStage != null` as the "is this a pipeline-driven task" check.
- **Step launch** — `launchStep` (`pipeline-runner.ts:573`), builds `composeArgs` (`:704`), calls `startTask(childId)` at `:780`. This is the hook point: either (a) intercept inside `startTask`/`startTaskInner` in `orchestrator.ts` (same pattern as today, just re-keyed), or (b) extend `composeStepPrompt`'s inputs before `launchStep` calls it. **(a) is lower-risk** — it means zero changes to PR #244's own files, everything lives in fork-owned `orchestrator.ts`.
- **Graph shape** — `shared/pipeline.ts`: `PipelineStep`/`PipelineGraph`/`PipelineEdge` types, `validatePipelineGraph` (`:322`), `resolveStartStep` (`:524`), `outgoingSteps`/`incomingSteps` (`:536`/`:549`), `resolveNextSteps` (`:861`), `classifyStepResponse` (`:792`), `newStep` (`:294`), `stepNameKey` (`:279` — case-insensitive name normalization, reused in §3 D3's fallback).
- **Handoff termination semantics — verified directly against code, not assumed:**
  - `resolveNextSteps` (`:861`) returns `{kind:"terminal"}` **only when a step has zero outgoing edges.** It never reads `handoff.status`.
  - `classifyStepResponse` (`:792`) short-circuits **only** on `handoff.status === "blocked"` → `"handoff-blocked"` (stays active, waits on Retry/manual-advance). A `status: "done"` handoff is **not** special-cased anywhere — it flows into `resolveNextSteps` like any other handoff and is subject to the same edge-resolution rules.
  - If a step has exactly one outgoing edge, `resolveNextSteps` takes it **unconditionally** — `handoff.next` is never even consulted.
  - **Conclusion: there is no "skip this step and jump ahead despite a modeled edge" primitive in the graph as built.** The only ways an execution path ends are (1) the step has zero outgoing edges (graph-structural), or (2) `status:"blocked"` (not a clean skip — it's an error state). This directly overturns my earlier assumption (from the prior conversation turn) that a Precheck step could emit `status:"done"` to skip Testing — it can't. See §3 D6 for the corrected design.
- **Fan-out is graph-static, not runtime-dynamic.** `transition:"all"` (`resolveNextSteps:` `if (transition === "all") return {kind:"steps", stepIds: dedupeStrings(outgoing.map(...))}`) launches **every authored outgoing edge**, unconditionally — the agent has no way to fire a subset. There is no "spawn N children where N is decided at runtime" primitive. See §3 D4.
- **Join** waits for every distinct `fromStepId` to arrive before firing (`join:"all"`) — arrival is presence-based, not content-based, so a no-op child's handoff still satisfies the join.
- **Migrations** — PR #244 ships `057_pipelines.sql`/`058_task_pipeline.sql`/`059_task_pipeline_id_index.sql` against *its own* base. Fork `main`'s migration tail is currently `068_pipeline_stage_state` with `054`–`059` free (post the v0.1.10 sync's renumbering of the old `051`–`059` pipeline block to `060`–`068`). **A renumbering pass will likely be needed again when #244 is pulled in** — same pattern used twice already (`migrations/index.ts`'s alias convention). Out of scope for *this* plan; flagged as a precondition of Wave 0 below.

## 3. Approach & key decisions

| # | Decision | Why / alternative rejected |
| --- | --- | --- |
| D1 | **Parallel rollout, not in-place replacement.** Keep `task.pipelineStage` orchestrator path fully intact. Build the new graph-based SDD pipeline as an additional, separate `Pipeline` definition. Both can run on real tickets side by side. | Retiring the old path before proving token/outcome parity on real work would be reckless given how much tuning O-1…O-15 represents. Matches the project's own "search before building" / measure-before-cutover discipline. |
| D2 | **Discriminator swap: `task.pipelineStage != null` → `isPipelineStepTask(task)`.** All of lean-context, CLAUDE.md filtering, effort tiering, and the deterministic-handoff injection move to fork-owned code in `orchestrator.ts`, hooked at the same `startTask`/`startTaskInner` choke point PR #244 already routes step tasks through. Zero changes to #244's own files. | Keeps the integration entirely fork-side and mergeable without waiting on upstream changes (other than the D3 extensibility ask, which has a fallback). |
| D3 | **Step-kind tagging: name-based convention now, swappable to a real field later.** A new fork-local lookup (e.g. `src/bun/sdd-pipeline.ts`, `stepKindForName(name): "non-coding"\|"coding"\|"review"`) keyed via `stepNameKey` (`shared/pipeline.ts:279`, already exported — reused, not reinvented) against the SDD graph's known step names. This is what CLAUDE.md filtering, review-diff caching, and effort tiering key off instead of a `pipelineStage` enum. If/when alamops lands the pitched `PipelineStep.kind`/`metadata` field, this single lookup function is the only thing that changes — a one-line swap from a name-match table to reading the field. | Unblocks work immediately without depending on his reply. Fragile point: renaming a step in the canvas editor silently breaks the mapping — acceptable for a fork-authored, rarely-renamed definition; would need the real field before recommending this pattern to other users. |
| D4 | **Fixed-N Build slots for Decompose → fan-out, not dynamic fan-out.** Since `transition:"all"` fires every authored edge unconditionally and there's no runtime-sized fan-out primitive, author a fixed number of `Build-1`..`Build-N` steps (N chosen to match `decomposePrompt`'s existing soft cap, e.g. 8). Decompose's deterministic output (harvested the same way `stage-handoff.ts` harvests today, not trusted purely to the agent's own handoff JSON) assigns real subtask content to slots `1..k` and marks slots `k+1..N` "no assignment — no-op." Each `Build-i` step's injected context (same step-launch hook as D2) carries either its real subtask or a no-op instruction ("end your turn immediately with a trivial handoff, no work needed"). `Code-Review`'s `join:"all"` waits for every slot's arrival, no-ops included — join arrival is presence-based, so this is safe. | The alternative — asking alamops for a dynamic/runtime-sized fan-out primitive — is a bigger, more speculative upstream ask than the `kind` field and isn't necessary to ship this. A no-op Build slot costs one cheap, near-instant agent turn; bounded, measurable in the token eval, not a structural blocker. |
| D5 | **Plan-Review human gate: repurpose "manual advance," don't fight the graph.** The Plan-Review step's instructions tell the agent to *never* auto-emit `next` (end every turn with `status` unset/no next, which — per the verified termination semantics above — leaves the execution sitting in `run.active`, not blocked, not advanced). The human reviews the plan in that step task's own panel and explicitly uses #244's manual-advance control to move to Decompose. | #244 has no built-in approval-gate concept (see prior turn's comparison). Manual advance already exists and does the job without needing an upstream feature request. Today's `planApproved`/`implementationApproved` booleans have no direct equivalent in the new model — this is a **behavior change**, not a straight port: the new flow relies on the human remembering to advance rather than the UI presenting an explicit approve/reject action. Flagged as an open UX question in §7, not silently accepted. |
| D6 | **Precheck is NOT a separate graph step — it's a step-launch-time context injection into Testing, same as today.** Corrected from the prior conversation turn's wrong assumption. Since there is no clean "skip a modeled edge" primitive (verified in §2), the deterministic precheck (`pipeline-precheck.ts` + `runTesterGate`'s logic) runs as part of Testing's own step-launch hook (D2's mechanism), computed right before Testing's task is created. When checks are all green and every `AC-N` is referenced from a test file, Testing's injected context tells it to do a **trivial confirm-only turn** instead of a full test run — cheap, but not free: unlike today's system (which can skip spawning the Tester agent entirely and jump straight to `done`), the graph model always spawns *some* agent turn at the Testing node. **This is a real, bounded token-cost regression versus the current full-skip behavior** — small (one cheap turn vs. zero), but should be measured explicitly in the parity run (§1.5), not assumed away. If it proves material, a future upstream ask (a conditional/skippable-edge primitive) is the fix — not attempted in this pass. | Matches what the graph model actually supports, verified against `resolveNextSteps`/`classifyStepResponse` rather than assumed. Keeps the integration honest about where it doesn't fully match today's behavior. |
| D7 | **No new migrations.** The integration reuses #244's `pipelines` table and `tasks.pipeline_id`/`pipeline_run`/`pipeline_parent_id`/`pipeline_step_id` columns as-is. The SDD graph itself is just a `Pipeline` row (JSON `graph` column) — data, not schema. | Simplicity; avoids a third renumbering pass on top of the one already needed to pull #244 in at all. |
| D8 | **Deterministic stage-handoff rides alongside, not instead of, the agent-authored `<handoff>` block.** Continue harvesting Read paths + succeeded commands deterministically and inject them into the next step's prompt via the same step-launch hook (D2) — layered on top of #244's own `composeStepPrompt` output (which already inlines the previous handoff), not replacing it. | Keeps the "agent can't forget to report it" reliability guarantee that #244's purely agent-authored handoff doesn't have, at no cost to #244's own mechanism. |

**Wave 1 — foundation (disjoint).**

Commit the exported JSON under `docs/pipelines/sdd.json` (or similar) so it's versioned and reproducible, not just clicked together once in a UI.

**Wave 2 — orchestrator hook (depends on T1).**
- **T3.** Re-key `pipelineLeanContext`/`resolvePipelineSystemPromptFile`/`resolveRunModel`/`resolveRunEffort` in `orchestrator.ts` to branch on `isPipelineStepTask(task) || task.pipelineStage != null` (both paths coexist per D1), routing pipeline-step tasks through `sddStepLaunchContext` (T1) for kind resolution instead of the `pipelineStage` enum. Verify `dropSettledStageSession`'s necessity under #244 (context note in §2) rather than assume it's redundant.
- **T4.** Wire the Testing fast-exit (D6): at Testing's step-launch, run the existing `pipeline-precheck.ts` checks, inject either the trivial-confirm context or the normal `## Pre-run checks` failing-tail context.
- **T5.** Wire review-diff caching (keyed on the Code-Review step by name/kind via T1) and repo-profile detect-once (unconditional, cwd-scoped, no kind-check needed) into the same hook.

**Wave 3 — validation.**
- **T6.** Run one real ticket through both the legacy `pipelineStage` flow and the new graph definition. Compare via `bun run eval:pipeline:tokens` (existing tool) plus a manual outcome-quality read. This is the actual go/no-go gate for §1's success criteria — not a formality.

**Out of scope for this plan:** retiring the legacy `pipelineStage` orchestrator path; any upstream PR against #244 itself (the `kind` field ask stays a comment until/unless alamops responds); a runtime-dynamic fan-out primitive.

## 5. Open questions / risks (surfaced deliberately, not glossed over)

1. **Plan-Review UX regression (D5).** Losing the explicit approve/reject UI action in favor of "just don't advance" is a real behavior change a human could get wrong (advance without having actually reviewed). Worth a lightweight mitigation (e.g. the step's instructions render a checklist in its own summary) — not designed here, flagged for T2/T3.
2. **Testing fast-exit token cost (D6)** is unmeasured until T6. If material, the honest fix is a future upstream ask, not a workaround bolted onto this integration.
3. **#244 is still under review upstream** — review rounds 1-4 already changed real runner semantics (e.g. the step-cap-extension behavior, the done/restart split). A 5th round before merge could change `resolveNextSteps`/`classifyStepResponse` again; re-verify §2's termination-semantics findings against whatever actually lands before starting Wave 2.
4. **Migration renumbering (Wave 0)** is a known, already-solved pattern (done twice this session) but still real work and a real risk window — full test-suite verification required before fast-forwarding `main`, same discipline as the v0.1.10 sync.
